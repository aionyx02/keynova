## COMPLETED: PERF.1.FU memory pass — release profile + host WS trim

User-directed, quality-neutral memory work. Two levers:

- **B1 — `[profile.release]` added** (`strip = true`, `lto = "thin"`,
  `codegen-units = 1`). There was no release profile before, so release used
  cargo defaults. Binary `25,101,824 B (23.9 MB)` -> `23,582,208 B (22.5 MB)`,
  ~6% / 1.45 MB. The win is modest on Windows/MSVC because debug symbols live in
  the separate `.pdb`, so `strip` removes less than on Linux; LTO + cgu=1 mainly
  improve codegen quality. Runtime-quality-neutral; only release build time grows.
  Deliberately avoided `opt-level = "z"` and `panic = "abort"`.
- **A1 — `EmptyWorkingSet(GetCurrentProcess())` on hide** in `app/window.rs`
  (`trim_host_working_set`). The existing `SetMemoryUsageTargetLevel(Low)` only
  trims the WebView2 child processes; nothing trimmed the `tauri-app.exe` host
  WS. This pushes the host's resident pages out of the working set when hidden.
  Commit / private bytes are unchanged by design; pages fault back on next wake.
  This — not B1 — is the lever that should actually move the high release WS.

Verified: `cargo check --lib` + `cargo clippy --lib -- -D warnings` clean; release
build 0 errors. Reused the `windows` ProcessStatus/Threading API pattern already
in `observability.rs`.

Measured (release, this session) — resolves the open release-WS question:

- Release host `tauri-app.exe`: shown `32.1 MB WS / 8.5 MB PM`; hidden `34.7 MB
  WS / 11.1 MB PM` (stable to +30s). A direct-launch warm sample read
  `32.3 MB WS / 10.6 MB PM`. The host core is `~32 MB` regardless of shown/hidden
  — under the `200 MB` goal.
- Full process tree (host + 6 `msedgewebview2.exe`): `324.3 MB WS`. **This is the
  `273-335 MB` the docs called "release WS inflation" — it was the tree, not the
  host.** ~290 MB lives in the WebView2 children.
- Therefore A1 (host `EmptyWorkingSet`) is marginal in practice: it trims the
  already-small ~32 MB host, not the ~290 MB of WebView2 children. It is harmless
  (best-effort, hide-only) and kept. B1 stands as a clean binary-size/codegen win.
- Measurement note: GUI cold start under automation is slow/flaky (host can take
  >8 s to appear; control-plane handshake occasionally times out). Direct
  `Start-Process tauri-app.exe` + a poll-until-up loop was the reliable path.
- README memory table updated to the host-vs-tree split.

Private-vs-shared breakdown (release, owned-tree isolated via before/after
`msedgewebview2` PID diff — the children are not host descendants because WebView2
uses a shared runtime host) — this **closes PERF.1.FU**:

- Owned tree = 1 host + 7 webview children. Total `WS = 322.8 MB`, but
  `Private-WS = 79.7 MB`; the remaining `243.1 MB` is **shared Edge/Chromium DLL
  pages** that the OS stores once and every WebView2 process double-counts into its
  WS. Those pages are shared with the 12 unrelated WebView2 processes already on the
  machine — not a keynova-exclusive cost.
- keynova's real unique footprint is `~80 MB` (host `~8 MB` private + webview
  `~71 MB` private of necessary renderer/Blink/V8/network/storage), well under the
  `200 MB` background-core goal. The scary `324 MB` was a multi-process shared-page
  counting artifact.
- Decision (user, 2026-05-31): **close PERF.1.FU**. The only clean remaining lever
  (also `EmptyWorkingSet` the owned webview children on hide) was declined — it only
  pages out resident-private that faults back on wake, not worth the change. Process-
  model levers (`--single-process`, `--renderer-process-limit`, V8 heap caps) are
  rejected as quality-affecting / ADR-triggering.
