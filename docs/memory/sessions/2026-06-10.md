## COMPLETED: fix Ctrl+K close-then-reopen regression (focus-guard echo)

User-reported during release prep: pressing Ctrl+K to close the launcher
*sometimes* instantly reopens it. Branch `fix/ctrlk-reopen-guard` (from `main`).
Independent of the pin removal.

Root cause — a **second** close-then-reopen path the original CONT-era debounce
never covered. The backend keeps a `launcher_focus_guard` (`app/state.rs`) that
the frontend renews on every keystroke (`keepLauncherOpen`, 200 ms throttle,
**2000 ms** TTL — `dispatch.rs`). The window's `Focused(false)` handler
(`app/window.rs`) waits **1500 ms** then, if the guard is still valid, **re-shows**
the window (so the launcher stays open while you type and focus blips). But no
explicit-hide path cleared the guard: pressing Ctrl+K within ~500 ms of a
keystroke hid the window while the guard was still alive, so the delayed blur
task re-showed it. The 180 ms `TOGGLE_DEBOUNCE` in `shortcuts.rs` only collapses
*double-fired shortcuts*, not this guard echo — which is why the old fix "came
back" via a different route.

Fix: clear `launcher_focus_guard` inside `hide_launcher_window` (one chokepoint
covering the Ctrl+K toggle, Esc, and `cmd_hide_launcher`). The keep-open path
uses `show`, never `hide`, so clearing on hide never fights a legitimate
keep-open. `cargo clippy -- -D warnings` clean, `cargo test` 460 pass. Not
unit-testable (Tauri window runtime) — needs `tauri dev` manual smoke:
type → Ctrl+K → stays closed; type → Esc → stays closed; Ctrl+K with no recent
typing → toggles normally.
