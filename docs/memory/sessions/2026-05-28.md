  worktree; those were normalized to ASCII labels while preserving card

- Added final-response text fallback in `useCapabilityStream`.
- Added regression coverage proving the hook listens to `capability-response`
  and `capability-stream-chunk`, and renders final response text even without a
  chunk.

### Icon disk cache (out-of-band perf fix)

Symptom: first invocation after reboot stalled the search box because every
visible row triggered a fresh `powershell.exe + SHGetFileInfo` cold start
(~1–2 s each). Previous cache layer (`SEARCH_ICON_CACHE`) was in-memory only.

Root cause:

- `search_icon_data_url` in `src-tauri/src/platform/windows.rs` cached results
  in a process-local `OnceLock<Mutex<HashMap>>`. Cache was discarded on every
  process restart, so each session paid full extraction cost for every icon
  before the in-memory map warmed up.

Fix:

- Added a disk cache under `dirs::cache_dir()/keynova/icons/<hash>.b64` that
  stores the raw base64 PNG payload PowerShell already emits — no
  encode/decode hop on the hot path.
- Lookup order: in-mem → disk → PowerShell extract → write disk + in-mem.
- File name is `hex(sha256(icon_key))[..16] + ".b64"`. `icon_key` is already
  derived in `handlers::search::icon_key_for_item` and embeds `stable_hash(path)`
  for apps, so renames/upgrades miss the cache naturally (no invalidation logic
  needed).
- Failed extractions (`None`) stay in-mem only so a restart re-tries them in
  case the source app installed an icon later.

Out-of-band note:

- Not a REF.6.* subtask. Logged as a P0 startup-latency regression hotfix per
  user request; no ADR needed because the cache schema is fully reproducible
  from source state.

Verification:

- `cargo test --manifest-path src-tauri/Cargo.toml --lib platform::windows::tests`
  → 8 passed (3 new tests cover filename stability, uniqueness, and `.b64`/hex
  formatting).
- `cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings` → clean.
- Manual `tauri dev` smoke (cold reboot → palette open → confirm second-launch

### Terminal UI sizing fix (out-of-band UX fix)

Symptom: after running a builtin command that opened a terminal (e.g.
`/run …`), the `PaletteInputBar` above the terminal was clipped out of the
launcher window — the visible search box was gone. Separately, the terminal
viewport felt cramped at 342px.

Root cause:

- `useWindowResize.ts` defined a single `TERMINAL_HEIGHT = 360` used for both
  the full-screen terminal mode (no input bar visible) and the attached
  terminal returned from a builtin command (input bar still mounted above
  the panel). In the attached path, 360px was less than
  `PaletteInputBar (~64px) + .kn-terminal-header (~52px) +
  .kn-terminal-body (342px) + chrome`, so the input bar fell outside the
  configured window size.
- `.kn-terminal-body { height: 342px }` was hard-coded, capping the visible
  xterm viewport regardless of how much vertical space the launcher window
  could afford.

Fix:

- `.kn-terminal-body` height 342→460px (`src/index.css`).
- `useWindowResize.ts` `TERMINAL_HEIGHT` split into:
  - `TERMINAL_HEIGHT_MODE = 540` for `mode === "terminal"`.
  - `TERMINAL_HEIGHT_ATTACHED = 620` for `isTerminalResult(cmdResult)`.
- Suspense fallback placeholders raised 410→520px so the lazy chunk swap-in
  no longer pops the window height.

Out-of-band note:

- Not a REF.6.* subtask. Logged as a UI regression hotfix per user request;
  pure styling/numeric change, no ADR needed.

Verification:

- `npx tsc --noEmit -p .` clean.
- `npm run lint` clean.
- Manual `tauri dev` smoke (open builtin command that opens a terminal →
  confirm input bar still visible above terminal; switch to terminal mode →
  confirm the terminal body looks roomier) still owed by user.
