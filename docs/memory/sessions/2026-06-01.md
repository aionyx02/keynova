## Fixed: v0.3.0 Linux + macOS release CI failures

Diagnosed from the user-supplied failing release-workflow logs (the `v*` tag run).

Linux (`ubuntu-22.04`) — apt `exit code 100`, held broken packages:
- Root cause: `.github/workflows/release.yml` installed BOTH `libappindicator3-dev`
  AND `libayatana-appindicator3-dev`; the ayatana `-dev` package `Conflicts:`
  the old `libappindicator3-dev`, so apt refused to resolve.
- Fix: dropped `libappindicator3-dev` from the install list. Tauri v2 uses the
  ayatana appindicator; keeping only `libayatana-appindicator3-dev` is the
  current correct set.

macOS (`universal-apple-darwin`) — compile succeeded, then
`failed to bundle project Failed to copy binary from ".../release/keynova": does not exist`:
- Root cause: the crate has two bins — `tauri-app` (GUI, `src/main.rs`, the
  `default-run`) and `keynova` (control-plane CLI, `src/bin/keynova.rs`). The
  macOS bundler resolves the main app binary by case-insensitively matching the
  `productName` ("Keynova" → "keynova") against bin targets, so it picked the
  `keynova` CLI bin and looked for `release/keynova`. But the universal build only
  lipo's the app binary (`default-run` = `tauri-app`) → `release/tauri-app`
  exists, `release/keynova` does not. Windows is case-sensitive in this match, so
  it fell back to `tauri-app` and worked — hence Windows-only success.
- Fix: set `"mainBinaryName": "Keynova"` in `tauri.conf.json`. This explicitly
  overrides the app binary name (source = the `default-run` cargo output
  `tauri-app`, output = `Keynova`), bypassing the productName-vs-bin-name
  collision. It matches the inner-exe name Windows already produces, so no Windows
  regression, and does not rename the user-facing `keynova` CLI. The CLI's
  `gui_candidates` already lists `"Keynova"`, so `keynova start` still finds the
  bundled GUI.

Verification limit: the Linux apt fix is logically confirmed against the
conflict; the macOS `mainBinaryName` config is schema-valid (CLI 2.11.0) and JSON
parses, but the bundle itself can only be confirmed by the next macOS CI run — no
local macOS/Linux build is possible from this Windows host.
