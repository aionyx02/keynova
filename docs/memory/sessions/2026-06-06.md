# Session 2026-06-06

## COMPLETED: REF.7.D - qwen2.5:7b inline latency bench

Ran the REF.7.D quantitative reading after the user pulled `qwen2.5:7b`:
`npm run bench:ai -- --runs 10 --model qwen2.5:7b` (10 runs, host = Windows,
**CPU-only, no GPU**). Filled ADR-0029 §10 with the readings. Recording readings
is REF.7.D's defined deliverable; it does **not** change §4 Decision — ADR stays
`accepted`.

### Raw per-capability distribution (ms, 10 runs each)

| capability       | p50   | p95    | min  | max    |
| ---------------- | ----- | ------ | ---- | ------ |
| explain          | 7697  | 11788  | 2336 | 12447  |
| explain_stream   | 7715  | 11028  | 2389 | 11271  |
| fix_error        | 6869  | 10446  | 4644 | 10847  |
| gen_command      | 7740  | 11654  | 4719 | 11718  |

Pooled **inline** = `explain`+`fix_error`+`gen_command` non-streaming samples
(n=30): **P50 = 7598 ms, P95 = 11654 ms** (min 2336, max 12447).

### Result vs ADR-0029 §8 targets

- inline P50 7598 ms vs `< 800 ms` → **FAIL (~9.5x)**
- inline P95 11654 ms vs `< 1500 ms` → **FAIL (~7.8x)**
- palette warm open: filled from PRODUCT.1.H `PerfBadge` (~2.5 ms webview-side) →
  PASS\* (lower bound; excludes OS-press→webview time).
- palette cold open / search first-chunk P50: **not produced by `bench:ai`** (it
  only parses `[ai_capability_live]` AI lines). Left `pending` — they need their
  own harness, not faked from this run.

### Finding (decision-gated — not self-decided)

The inline latency gate fails by ~8-10x. The `< 800 ms P50` target reads as if it
assumed GPU or a much smaller model; ~7.6 s P50 is the honest cost of qwen2.5:7b on
this CPU host, not a code defect. Direction needs developer ruling — candidates:
(a) drop the inline default model to a small one (e.g. `qwen3:0.6b`) and re-measure;
(b) relax the §8 target and amend the ADR; (c) accept inline AI as a slow, explicit
opt-in and signal the expected wait in UX. `PRODUCT.2` unfreeze is gated on this;
kept **frozen** pending the ruling — not silently flipped.

### Small-model re-measure (developer chose "smaller default + re-bench")

Re-ran the bench on smaller models to test whether a small default meets the gate:

| model        | inline P50 | inline P95 | reliable           |
| ------------ | ---------- | ---------- | ------------------ |
| qwen2.5:7b   | 7598 ms    | 11654 ms   | yes                |
| qwen2.5:1.5b | 4266 ms    | 6269 ms    | yes (10/10 clean)  |
| qwen3:0.6b   | ~4-5 s     | —          | **no** (empty responses; bench aborted on run 4) |

Conclusion: 4.6x fewer params (7b→1.5b) only halved latency — **the best reliable
small model still misses 800 ms by ~5.3x**. The wall is CPU token-generation
throughput, not model size; no locally-reasonable model hits the target on this
host. qwen3:0.6b is a reasoning model whose `<think>` tokens consume the 512-token
budget → intermittent empty replies → unfit as a default. Also found: there is no
single hardcoded inline default to flip — `model_manager.recommend_models` is
already hardware-tiered (recommends `qwen2.5:1.5b` on low-spec), and
`handlers/ai.rs`'s `qwen2.5:7b` is only the empty-recommend fallback. So "change
the default model" reduces to changing the §8 reference/target, not a code constant.
Direction (a) (swap model only) is proven insufficient; the live decision is now
(b) relax §8 target + amend ADR and/or (c) slow opt-in, optionally adopting
qwen2.5:1.5b as the reference default. Awaiting developer ruling.

### Resolution (developer-approved): tiered §8 target + 1.5b reference default

aspirational, add a **CPU-host tier `P50<5000 / P95<8000 ms`**; (2) adopt

`qwen2.5:1.5b` (P50 4266 / P95 6269) **PASSES the CPU-host tier**; `qwen2.5:7b` stays
a higher-quality option that exceeds the CPU tier.

## PRODUCT.3: secret-gated code-signing pipeline

Developer asked to wire signing now and supply certs later (AI cannot sign — no
cert/key; self-signed rejected as misleading + key-in-repo). Scaffolded so signing
activates purely from CI secrets with **zero behavior change until secrets exist**.
ADR-0048 (proposed) documents the decision + required secrets.

- `release.yml`: build job gains `env:` mapping `WINDOWS_CERTIFICATE(_PASSWORD)`
  from secrets; a gated `Prepare Windows code signing` step
  (`matrix.platform == 'windows-latest' && env.WINDOWS_CERTIFICATE != ''`) decodes
  the base64 PFX, imports it, and injects the thumbprint into tauri.conf.json on
  the runner. tauri-action step gains `APPLE_*` + `KEYCHAIN_PASSWORD` env
  passthrough (macOS signs/notarizes only when non-empty).
- `tauri.conf.json`: `bundle.windows` gains inert `digestAlgorithm: sha256` +
  `timestampUrl` (no-ops until a thumbprint is present).
- Private key never enters the repo; only inert params + gated CI logic are tracked.
- Updater-artifact signing (`TAURI_SIGNING_PRIVATE_KEY`) is a separate item, out
  of scope. The signed path is untested until real certs land — verify on first
  signed run. `security.md` §9 row updated.
